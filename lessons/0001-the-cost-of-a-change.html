Part I · Module 1 · Lesson 1

The cost of a change

About 10 minutes · Goal: locate duplicated knowledge before choosing an abstraction.

Mission connection: an AI agent can produce a passing patch while leaving the next change harder. Your job is to evaluate where the knowledge lives—not merely whether today's output works.

1. Start with a changing fact

Software encodes knowledge: when cancellation is allowed, what capacity means, how a payment is identified. If one business fact has several independently maintained representations, changing that fact requires finding and coordinating them all. Missing one can make the system contradict itself.

Hunt and Thomas emphasize that DRY concerns knowledge, not just repeated lines. They also describe maintenance as ongoing work, not a phase that starts after release. Read the official extract, especially “DRY is More Than Code.”

For this exercise, call the spread of work required by one conceptual change change amplification. We will judge designs by a concrete change scenario, not by a universal file-count score. Several files can change for good reasons.

2. A small worked contrast

A workshop currently permits cancellation until 24 hours before its start. The preview and server enforcement both implement that policy:

// ui/cancellation-preview.ts
const allowed = hoursUntilStart >= 24;

// server/cancel-booking.ts
if (hoursUntilStart < 24) return reject("Too late");

The two expressions look different, but encode the same rule. Changing only the preview would not change server enforcement. Changing only enforcement would leave the preview misleading.

A possible improvement is one authoritative policy module, exercised through a meaningful interface:

type CancellationDecision = {
  allowed: boolean;
  reason: string;
};

function cancellationDecision(
  hoursUntilStart: number
): CancellationDecision {
  const allowed = hoursUntilStart >= 24;
  return { allowed, reason: allowed ? "Within policy" : "Too late" };
}

This is a sketch, not production architecture. A shared library may work when the UI and server can use it; otherwise the server might expose the decision. The server must still enforce it at cancellation time. A preview can become stale. Validate real timestamps and clock assumptions in a production implementation.

Notice what we did not build: a configurable policy engine for every future business rule. Localizing an actual shared fact is different from predicting every future variation.

3. Tactical, strategic, speculative

  • Tactical patch: update the known comparisons and ship. It may be appropriate under incident constraints, but the coordination burden remains.
  • Strategic investment: give the policy an authoritative home, simplify callers, and verify behavior. The extra work has a specific payoff under the next policy change.
  • Speculative overengineering: introduce an elaborate generic engine without concrete requirements. More machinery is not automatically more foresight.

These contrasts are our instructional synthesis. Later readings deepen Ousterhout's distinction between tactical and strategic programming and Evans's separate concept of strategic domain design. They are not synonymous.

4. Your turn — reason before editing

Scenario: The business now requires a 48-hour cancellation cutoff. Reminder emails must still be sent 24 hours before the workshop. Treat hoursUntilStart as a validated number for this exercise.

// cancellation-preview.ts
export function canShowCancel(hoursUntilStart: number) {
  return hoursUntilStart >= 24;
}

// cancellation-command.ts — authoritative enforcement
export function canCancel(hoursUntilStart: number) {
  return hoursUntilStart >= 24;
}

// reminders.ts — separate scheduling rule
export const reminderLeadHours = 24;

  2. Propose one modest design improvement. Write a tiny code sketch or describe the interface and callers. Explain what callers no longer need to know.
  3. Name two tests at the cutoff boundary, including their expected outcomes.
  4. An AI agent proposes putting all three values into HOURS_BEFORE_WORKSHOP. Write a short review accepting or rejecting that change and explaining why.

Transfer question: If cancellation in the preview and command came from two genuinely independent business policies that merely happened to match today, would your design still be appropriate? What fact would you ask the business to clarify?

Need a hint? Try retrieval first.

Ask “what business fact would cause this expression to change?” for each location. Identical values need not have the same reason to change. Tests immediately below and exactly at a threshold distinguish inclusive from exclusive rules.
