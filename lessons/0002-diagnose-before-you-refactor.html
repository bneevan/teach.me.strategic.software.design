Diagnose before you refactor

About 12 minutes · One skill: name a maintenance difficulty and support it with evidence.

Mission connection: “make it cleaner” invites an AI agent to optimize appearances. A diagnosis tells it which burden must actually decrease—and what must remain true.

1. Recall before reading on

Without opening Lesson 1, answer briefly:

  1. Why test exactly at an inclusive cancellation cutoff, not only below it?
  2. If reminders and cancellation share a lead-time constant, what goes wrong when only cancellation changes?

Keep these answers for your reply. Retrieval matters more than polished wording.

2. Complexity is difficulty, not size

Ousterhout's CS 190 introduction, “Complexity” section, frames software complexity in terms of how structure makes a system hard to understand and modify. It names dependencies, inconsistencies, and special cases as contributors, and emphasizes eliminating or hiding complexity because a large system cannot fit in one person's mind.

Our working question is therefore not “How many lines are there?” but “What must the maintainer understand, find, and coordinate to make this change safely?”

Use three diagnostic questions. They can overlap; they are not exclusive categories:

  • Change amplification: how many representations of one decision must change together? You practiced this in Lesson 1.
  • Cognitive load: what facts must someone keep in mind to perform the task correctly—units, meanings, ordering, exceptions?
  • Unknown unknowns: what relevant obligation might someone fail to discover at all? Once discovered, it is known; the design problem was that the need to look was not apparent.

A dependency is a relationship that makes one piece of code rely on another's details or behavior. Dependencies can create all three difficulties; they are not a fourth symptom at the same level. Some dependencies are necessary. The goal is to make them appropriate, understandable, and local.

3. A short function can be expensive to use

// cancellation-policy.ts
// Caller must refresh the rules before making a decision.
export function canCancel(hoursUntilStart: number) {
  return hoursUntilStart >= cachedRules.noticeHours;
}

The comparison is tiny, but a caller must know about a cache, a refresh operation, and when refreshing is required. That knowledge is part of the effective interface, even if the function signature does not show it.

Weak response: extract the comparison into another one-line helper. The refresh obligation remains.

More useful direction: investigate whether the policy module can own rule loading and freshness, or accept an explicit rule snapshot with clear guarantees. Either choice has trade-offs: loading may introduce latency and failure; snapshots require an explicit freshness contract. Do not promise hidden I/O is always better.

A comment can make an obligation discoverable. It does not necessarily remove the obligation. We want less knowledge for callers to coordinate, not merely more prose explaining the coordination.

4. Your task: diagnose a real maintenance trap

The following is illustrative TypeScript. Assume remainingHours is valid, rule refresh succeeds, and the preview is advisory. The server must enforce current policy when cancellation is requested. Two shown paths already work:

// preview.ts
await refreshCancellationRules();
return canCancel(remainingHours);

// cancel-command.ts
await refreshCancellationRules();
if (!canCancel(remainingHours)) return reject("Too late");
return performCancellation();

A new AI-generated path skips that sequence:

// mobile-cancel-command.ts
if (!canCancel(remainingHours)) return reject("Too late");
return performCancellation();

The policy module silently starts with a cached 24-hour cutoff. The current business cutoff is 72 hours. A refresh updates the cache. Tests run in a fresh process where no other caller refreshes it. A developer inspecting the new command's function signature sees no rule-refresh dependency.

  1. Predict: a mobile user tries to cancel with 48 hours remaining. What does this implementation do, and what should it do?
  2. Diagnose: identify one concrete cognitive burden and one obligation that could escape discovery. Explain why a short function and a passing happy-path test would not settle the design question.
  3. Review: the agent offers “add await refreshCancellationRules() to the mobile path.” Is that an adequate immediate repair? What maintenance burden remains?
  4. Guide: write a two- or three-sentence agent instruction aimed at reducing that burden. Require a behavioral regression test with an expected outcome and name one trade-off to investigate. No implementation required.
Hint — use only after an attempt

Separate a fix for this caller from a design that prevents future callers forgetting the same requirement. Ask what a new caller must know besides the visible argument. Test the stale-rule condition, not only a value all possible cutoffs accept.
