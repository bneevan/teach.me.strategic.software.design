Diagnose before changing structure

Complexity: difficulty understanding or modifying software that arises from its structure. Judge it against a concrete maintenance task, not line count alone.

Three diagnostic questions

Change amplification
What must change together? Example: one cancellation rule independently encoded in several callers.
Cognitive load
What must someone keep in mind to do the task correctly? Example: refresh shared rules before calling a decision function.
Unknown unknowns
What relevant obligation might someone not realize they need to discover? Example: a decision function silently relies on a refresh absent from its visible signature or discoverable usage guidance.
Dependency
A relationship in which code relies on another part's details or behavior. It can create several symptoms above; not every dependency should be removed.

A diagnosis in four lines

  1. Task: state the change or behavior under review.
  2. Evidence: name the obligation, location, or execution sequence.
  3. Consequence: predict how maintenance or behavior goes wrong.
  4. Verification: specify a case, expected outcome, and what would count as improvement.
Agent instruction pattern

“This caller must currently remember [obligation]. Investigate a design where [owner] owns it, keeping [invariant] true. Add a regression for [failure condition] expecting [outcome], and report trade-offs and checks actually run.”

Useful distinctions

  • A tactical repair can be correct while leaving an ongoing design burden.
  • Documenting an obligation improves discoverability; eliminating a caller obligation reduces required knowledge.
  • Short functions can have large effective interfaces.
  • Hiding loading inside a function can add latency and failure modes. Account for them explicitly.
  • An unseen file is not automatically an unknown unknown. Ask why a relevant dependency would be missed.
